# PB 榜开发计划

状态：PB 后端、人数缓存、前端排行页面与子路由、拆分组件及配套测试文件已实现。扫雷网规则与 PB 后端分别位于 `saolei/`、`pb/`。本文保留设计依据，并记录实施状态；实际接口、命令与测试用法见 [app README](README.md#pb-榜)。测试文件已实现不代表 Cypress 已运行。个人 PB 界面等待单独计划；扫雷网规则依赖 PB 仍为后续优化。

## 定位与规则

PB 榜是一个新的大榜，也是“一份大榜 hash + 多个小榜 zset”约定的明确例外。不要沿用 Saolei.wang 的八项纪录结构，也不要把 PB 当作所有竞速榜的默认实现。

- 接收 BEGINNER、INTERMEDIATE、EXPERT，即 `b`、`i`、`e`。
- `mode` 固定为 STD，`state` 固定为 OFFICIAL，排除 `ongoing_tournament=True` 的隐藏录像。
- 数据前提：`bv` 一定是正整数，`timems` 一定是非负整数，不额外设置空值或正数准入筛选；`timems = 0` 可以入榜。
- 每个 `(level, bv)` 是一个小榜，每个用户只保留该桶内 `timems` 最小的录像。
- NF 另设分榜，依据 `right_ce == 0`，不是旧的 NF mode 编码；普通 PB 榜也包含 NF 录像。
- 排序 score 包含 `timems` 与分钟级 `upload_time`，更快优先，同用时上传分钟更早优先；同分同分钟不进一步区分上传时间。
- 固定 `level`、`bv` 时，Bvs 和 Stnb 都随 Time 单调变化，不需要分别维护排序索引。

`timems > 0` 时，前端由原始毫秒用时计算：

```text
seconds = timems / 1000
bvs = bv / seconds
stnb = coefficient[level] * bv / seconds ** 1.7
coefficient = {b: 36, i: 162, e: 435}
```

零用时极为罕见，仅可能在 `bv = 1` 时出现。`timems = 0` 时，Time 排序及 score 编码仍然有效，前端允许将 Bvs/Stnb 展示为正无穷大（`Infinity`）。派生值由前端计算，API 仍返回整数用时，不需要传输无穷大数值。该边界不影响 PB 准入，不额外增加筛选条件。

## 缓存方案

以下为已实现的 key 命名。

| 用途 | 类型 | 示例 key | 内容 |
| --- | --- | --- | --- |
| 某个 PB 小榜 | zset | `speedranking:pb:std:b:10` | score 编码用时及上传时间，member 编码用户 id 和录像 id |
| 对应 NF 小榜 | zset | `speedranking:pb:nf:b:10` | 同上，只接收 NF |
| 某个用户的 PB 索引 | hash | `speedranking:pb:player:48` | field 标识普通/NF、level、bv；value 保存该桶的个人纪录 |
| 各 PB 小榜人数 | hash | `speedranking:pb:counts` | field 与用户 hash 相同，value 为小榜人数 |

每个小榜没有成绩 hash；每个用户拥有一个 hash。用户 hash 的 field 必须区分普通/NF，否则同一个 `(level, bv)` 下的两条纪录会互相覆盖。

不限制缓存人数，不使用请求自动回填。录像数据库是事实来源，Redis 保存所有用户已有的 PB；没有成绩的桶无需提前创建 key。

### 用户 hash 中的 rank

设计时按包含 NF 在内约 500 个实际有成绩的小榜估计规模，不是固定枚举数量。当前前端的三个等级范围含普通/NF 共 1302 个可选桶，实际 Redis key 按已有成绩创建。用户全部 PB 查询应主要读取用户 hash，不在每次请求中逐个查询所有小榜的 zset。pipeline 虽然能降低往返开销，但不能消除大量排名查询的执行成本；先前建议以逐桶 ZRANK 取代 rank 缓存，没有充分考虑这个规模。

确定保留 rank hash，当前用户 hash 的 JSON 保存 `timems`、`rank`、`video_id`。录像 id 是必需字段，用于返回录像链接、定位旧 member、替换或删除纪录。旧录像 id 直接从已读取的 rank hash 获取，用用户 id 和录像 id 构造旧 member，不额外查询数据库或搜索 zset 来定位录像。

不为日常增量选优强制保存完整 `upload_time`。重建时可直接使用数据库的原始上传时间；未来 Saolei.wang 依赖 PB 时，是否需要额外保留该信息，再随其 tie-breaker 策略讨论。

需要区分个人纪录更新和排名缓存刷新：其他用户新增、改善或删除成绩，也可能改变本用户的 rank。仅在本用户破纪录时更新 rank 不足以维护全榜排名。

当前按一次受影响人数不足 1000 人的规模设计；达到该规模时服务器会升级，届时再评估性能。每次小榜顺序变化后，立即同步批量刷新受影响用户 hash 中的 rank，不引入后台任务、定时刷新或跨事件合并。

刷新只针对本次变化的小榜及其排名区间，不遍历约 500 个小榜。替换纪录刷新旧、新排名之间的闭区间；加入或移除刷新从变动位置到榜尾。一次批量业务操作对同一小榜的修改集中提交，人数不变时取旧、新位置覆盖的范围，人数改变时从最早变动位置刷到榜尾。通过 pipeline 查询变化 member 的旧、新排名，再读取区间并批量更新用户 hash，不逐用户执行 ZRANK。全量重建仍逐小榜刷新整榜。

同步刷新不代表读写全过程具有并发快照保证，仍遵循后文的并发及手动修复边界。不预先增加面向更大规模的调度机制，也不在未实测时承诺固定毫秒耗时。

### 小榜人数 hash

页面需要在选择 3BV 前显示各小榜人数，因此增加独立的 `speedranking:pb:counts` hash，而不是让浏览器逐榜请求人数。field 使用 `std:{level}:{bv}` / `nf:{level}:{bv}`，与用户 hash 一致。

`PBRankingCache.refresh_ranks` 在读取受影响区间的同一个 pipeline 中执行 ZCARD，再通过写入 pipeline 更新人数和区间内用户的 rank。单录像、批量更新、管理员修复以及全量重建共用这一方法。空榜保存 0，尚未创建的 field 也按 0 处理。

`GET /api/speedranking/pb/counts` 通过一次 HGETALL 返回全部人数。小榜分页仍直接使用目标 zset 的 ZCARD 获取 `count`，不依赖人数 hash；并发更新时两次请求的人数可能短暂不同。页面加载和手动刷新时获取人数，切换 NF、等级或 3BV 时复用已加载的人数。

### member 编码与唯一性

member 确定使用带分隔符的十进制字符串 `user_id:video_id`，例如 `48:123456`。它便于解析，不补齐位数。排序主次项已经在 score 中，id 不需要按数值顺序参与 tie-breaker；score 完全相同时，Redis 的字符串顺序仅提供一个稳定但无业务优先级的次序。[Redis ZADD 文档](https://redis.io/docs/latest/commands/zadd/)

不采用固定宽度拼接、二进制编码或 Base62，不引入压缩依赖。

注意：Redis 去重依据整个 member，不是 `user_id`。`48:123456` 和 `48:123457` 可以同时存在，因此每次替换必须删除旧 member，加入新 member，并更新用户 hash。仅调用 ZADD 无法保证“一用户一成绩”。[Redis ZADD 文档](https://redis.io/docs/latest/commands/zadd/)

替换时，rank hash 已提供旧录像 id，无需额外查找旧纪录；相对于纯用户 id 的 member，主要增加的是旧 member 的 ZREM。复合 member 能在榜单分页中直接返回录像 id，避免逐行查用户 hash。

## score 编码

PB 小榜没有成绩 hash，分页接口需要从 score 恢复原始 `timems`。因此这里不能直接沿用 Saolei.wang“score 仅用于近似排序，不解码成绩”的约定。

确定使用整数编码，时间起点为 Unix epoch（UTC `1970-01-01 00:00:00`）：

```text
M = 2**26 = 67_108_864
upload = 从 Unix epoch 算起的 UTC 整数分钟数
score = timems * M + upload
0 <= upload < M
timems = integer_score // M
```

用时保留整数毫秒；上传时间确定截断到分钟，但不能发生进位污染用时。Redis double 可以准确保存绝对值不超过 `2**53` 的整数，因此按保守上限 `2**53 - 1` 检查整个编码范围。[Redis ZADD 文档](https://redis.io/docs/latest/commands/zadd/)

当前 `videomanager.models.MAX_TIMEMS = 99_999_999`，比 Saolei.wang zset 的单项上限 999999 大。PB 接受模型的完整范围，需要满足：

```text
(99_999_999 + 1) * M - 1 <= 2**53 - 1
M <= 90_071_992
```

不能直接复用现有 `M = 3_000_000_000`：它在完整模型用时范围内超出精确整数容量。也不能未经确认，把 PB 的准入用时上限降低到 Saolei.wang 的上限。

确定采用 `M = 2**26 = 67_108_864`，最大 score 为 `6_710_886_399_999_999`，仍在上述范围内。

分钟级精度可覆盖约 127.60 年（按 365.2425 日/年），最后可表示的分钟是 UTC `2097-08-05 09:03`。时间起点和编码系数固定，不随重建改变。

按预期，时间编码超限之前会更换架构，不为遥远的超限情况设计自动扩容或兼容机制。当前编码仍须满足已选范围，避免上传部分进位污染 `timems`；榜单返回的整数毫秒用时必须准确，同用时同分钟的用户之间允许任意稳定顺序。

重建时可以按原始 `timems`、完整 `upload_time` 选出录像，再编码写入缓存。正常增量更新以实现简明为主，直接比较新旧 score，较小才替换，相同则保留现有纪录，不为同用时同分钟的录像进一步查询完整上传时间。

因此，重建可能更换同用时同分钟下的录像 id，但不改变该用户的 PB 用时及编码 score。不要为了让日常更新与重建在这类并列情况下选择完全相同的录像，增加细粒度时间追踪逻辑。

## 查询与性能

### 查询一个小榜

由普通/NF、`level`、`bv` 直接定位 zset，读取人数及 `ZRANGE ... WITHSCORES` 分页结果。从 member 解析用户 id、录像 id，从 score 恢复毫秒用时。

接口采用现有 `start/end` 左闭右开约定，并限制单次条数。不扫描所有 key，不逐行查数据库或用户 hash；用户资料继续通过已有批量接口获取。

### 查询一个用户的所有 PB

一次读取该用户 hash，返回已有的普通/NF、`level`、`bv`、用时、录像 id 和缓存 rank。无需每次请求遍历约 500 个小榜，也不逐项回源数据库。

ZRANK 可以用于定点排名校验或修复，而不是作为用户全部 PB 请求的默认读取路径。Redis 的排名从 0 开始，缓存和接口统一使用从 1 开始的排名。[Redis ZRANK 文档](https://redis.io/docs/latest/commands/zrank/)

小榜变化后立即批量刷新 rank，使用 pipeline 降低往返和 socket 开销。全量重建等较大的操作仍需分段处理，避免一次排队过多响应。[Redis pipeline 文档](https://redis.io/docs/latest/develop/using-commands/pipelining/)

总体内存与“用户实际拥有的 PB 桶数量”成正比，而不是所有录像数量。用户 hash 和 zset 存在部分重复数据，但分别服务用户查询和小榜查询，是合理的双向索引成本。

## 更新与补位

保持“共同读取、独立判断、共同写入”的机制，但 PB 使用自己的缓存方法，不强行套用 `SpeedRankingCache` 的固定大榜 hash 结构。

- 单录像加入：只处理对应用户、level、bv 的普通/NF 桶；从 rank hash 获得旧录像 id，构造旧 member，读取其 score，与新 score 比较，较小才替换，同分保留现有纪录。
- 单录像变差、失效或删除：先判断该录像是否保持当前 PB；不是纪录则跳过，是纪录则从数据库查询该桶的替补或清空。
- `player`、`level`、`bv`、NF 资格发生变化：旧桶移除并补位，新桶尝试加入；状态与比赛隐藏资格变化也应覆盖。
- 批量加入：当前通过窗口函数，分别查询普通/NF 的 `(player, level, bv)` 桶内最佳录像，按原始 `timems`、完整 `upload_time`、id 排序；再按 score 与已有缓存纪录合并，同分保留缓存中的录像。尚未实现“普通最佳也是 NF 时复用”的查询优化。
- 批量移除：收集实际受影响的桶并去重，只查询需要补位的纪录；按玩家 id 分段，避免一次加载所有候选录像。
- 写入：先读取变动 member 的旧排名，再将旧 member 的 ZREM、新 member 的 ZADD、用户 hash 中个人纪录的 HSET/HDEL 放在同一事务 pipeline 中提交。随后读取新排名，立即同步批量刷新受影响区间内用户的 rank 和小榜人数；个人纪录提交与后续刷新不是同一个事务。个人纪录刚写入时 `rank` 暂为 `None`，区间刷新后填入从 1 开始的排名。

数据库事件在事务提交后处理；Redis 写入不参与数据库回滚。不自行恢复 WATCH 或引入全榜锁。读后写仍可能发生竞争；复合 member 还可能因竞争留下同用户多条成员，这一点比现有纯用户 id 的 member 更需注意。事务 pipeline 只能保证该次写入集中执行，不能保证先前读取未过期。

遵循整个 app 的[更新错误日志规则](README.md#更新错误日志)：个人纪录更新、rank 刷新、管理员修复或整榜重建发生错误时，必须记录异常堆栈及相应榜、用户、录像或批次上下文。尤其是个人纪录已经提交、后续 rank 刷新失败的情况，不能静默忽略。日志要求不额外引入重试或并发保护，也不改变原有异常传播方式。

性能和实现简明优先。PB 排行完全由 Redis 缓存实现，调整灵活、重建成本低；暂不增加 WATCH、锁或并发重试等保护机制，接受竞争引起的暂时不同步。保留管理员单项修复和整榜重建，出现实际问题后再决定是否需要针对性的并发控制，不预先解决尚未出现的竞争问题。

管理员重建需要能清理目标桶中该用户的多余旧 member，而非只相信可能已经不同步的用户 hash；可以在修复路径扫描该小榜，不让正常更新承担全榜扫描成本。

数据库查询先复用现有 QuerySet、窗口函数和分段刷新方案，不增加通用查询框架。现有 `(level, mode, player, pluck)` 索引不是 PB 专用索引；针对 `(player, level, bv)`、资格筛选及 `timems/upload_time` 的补位查询，先在 MySQL 8.4 用 EXPLAIN 验证，再决定是否新增联合索引。需要模型变更时使用 makemigrations。

## 配套工具与实施状态

以下步骤已完成。这里列出已存在的实现，不将其继续作为待开发任务；个人 PB 界面暂不实施。

2. 实现 PB 专用缓存基础读写和选优函数，不改现有 Saolei.wang 的业务函数。
3. 实现单录像与批量录像加入、移除和补位，接入已有上传、审核、标识、比赛公开、删除等刷新入口。
4. 添加 `rebuild_pb_ranks` 管理命令，按玩家 id 分段，从数据库分桶选优，写入普通/NF zset 和用户 hash；小榜构建完成后再生成用户 hash 的 rank 和人数 hash。支持 `--batch-size` 与每批进度输出。本地初始化 `dangerzone.init_local_test` 在导入快照后也会重建 PB 榜。
5. 添加管理员 Ninja API，指定用户 id、level、bv、普通/NF，从数据库强制重建这一项，无候选时同时清除两侧缓存，并按确定的策略刷新受影响排名。单项修复不依赖整榜重建。
6. 添加小榜分页、用户全部 PB、各小榜人数三类只读 API，均从 Redis 取数据；前端计算 Bvs/Stnb。
7. 添加后端测试：编码边界及用时还原、桶内选优与 NF、替换/删除及分类迁移、受影响排名区间、批量更新、人数刷新与重建、管理员清理重复 member，以及更新错误日志。
8. 实现前端 PB 页面，拆分为请求与分页入口 `PBRanking.vue`、人数选择组件 `PBBVButton.vue`、纯渲染组件 `PBRankingTable.vue`，格式化及请求函数位于 `pbRankingService.ts`。
9. 将各大榜拆为竞速入口的子路由，PB 路径为 `/ranking/speed/pb`；`SpeedRanking.vue` 仅负责选择大榜与渲染 `RouterView`。
10. 添加对应 Vitest 和 Cypress 测试文件。页面测试保留请求、分页、NF/3BV 联动与失败重试；按钮和表格的细节分别在其组件测试中覆盖，避免页面重复测试。不要扩充无业务价值的减功能测试。

初版全量重建采用简单方案：暂停 PB 相关读写，清空 PB 命名空间，按玩家分段构建，最后逐小榜刷新 rank。没有临时命名空间或原子发布；错误记录日志并中断，可能留下部分缓存，排除错误后重新运行整个命令。只清理 PB，不影响扫雷网缓存和录像数据库。不引入无停机双写、增量回放等复杂机制，不承诺无停机切换。

## 前端实现

- PB 小榜表格按排名、PlayerName、Time、Bvs、Stnb、上传时间排列，使用 ElTable；点击行通过 `row-click` 预览录像，点击玩家名仍跳转资料页。上传时间显示到用户本地时区的分钟，零用时的 Bvs/Stnb 显示 `Infinity`。
- `PBRanking.vue` 使用 ElPagination，将页码与每页条数换算为 API 的 `start/end`；NF、等级、3BV 或每页条数变化时回到第一页。人数和榜单分别维护加载、错误状态，忽略过期响应，手动刷新会重新请求两者。
- `PBBVButton.vue` 每个等级一个按钮，点击展开交互式 tooltip。3BV 范围为初级 1–54、中级 1–216、高级 1–381；这是前端选择范围，后端 API 只要求 `bv > 0`，不把这些上限用作缓存准入条件。
- 网格每行十个数位，左侧显示 `bv // 10`，滚动区域外的顶行显示 `bv % 10`。按钮显示人数而非 3BV；0 人禁用，整行有效桶均为 0 人时隐藏，范围外留空。选中后发出 3BV 并关闭弹层。
- `PBRankingTable.vue` 只根据 `rows`、`level`、`bv`、`first`、`loading` 渲染，不请求数据；排名按 `first + index + 1` 计算。
- 大榜子路由支持直接访问与浏览器返回，选择器与路由同步。NF、等级、3BV 和分页仍是 PB 组件内部状态，当前不编码到 URL。

## 后续：Saolei.wang 依赖 PB

已确认：Saolei.wang 依赖 PB 在数学上可行，但作为独立的后续优化，不与 PB 首次上线同时迁移。PB 首次上线保持现有 Saolei.wang 更新链路不变。

对于某个等级、某个 bv，最小 Time 就是最大 Bvs。只要 PB 覆盖全部合格录像，Saolei.wang 可以在满足自身 bv 门槛的 PB 桶中选择最小 Time 或最大 Bvs，无需再次遍历全部录像。Stnb 同样可以由桶的最佳 Time 派生。主成绩选优可等价复用，但完整上传时间 tie-breaker 的兼容性需要另行讨论，不能宣称两套选优在所有并列情况下完全一致。

- 重建：PB 构建完成后，再依据每个用户的 PB hash 重建 Saolei.wang；不读取构建到一半的数据。
- 加入或改善：只有个人 PB 改变，才需要用该 PB 候选尝试改善 Saolei.wang 纪录。
- 删除、变差或失去资格：如果丢失的 PB 保持 Saolei.wang 纪录，需要从该用户剩余合格 PB 桶重新选优，不能只与新替补比较，也不能只处理“破纪录”。
- 时间精度：日常 PB 更新不追踪同分同分钟内的完整上传时间差异。未来依赖 PB 的 Saolei.wang 若仍要求原始上传时间精度，需要单独确定取值与修复方案，或接受相应简化；不要提前把这项追踪强加到 PB 更新链路。
- 规则边界：PB 准入不能遗漏 Saolei.wang 需要的录像；尤其不能照搬 Saolei.wang zset 的数值上限来丢弃原始 PB 数据。
- 普通/NF：两套 PB 数据分别服务对应的 Saolei.wang 纪录，不能只用普通 PB 推导 NF。
- 修复：继续保留各小榜管理员修复 API；PB 缓存缺失或错误时，是否先修 PB、再修依赖榜，需要提供明确流程。

“PB 没改变就不刷新 Saolei.wang”只适用于缓存原本正确且规则不变的正常增量流程，不能替代管理员强制修复或规则修改后的重建。

## 总体判断

按 bv 分桶能消除同桶内 Bvs/Stnb 的独立选优，并给多个大榜提供较小的候选集合，值得实施。zset 服务小榜查询，带 rank 和录像 id 的用户 hash 服务个人查询，避免每次查询遍历约 500 个小榜。主要成本集中在替换旧 member、动态桶补位以及 rank 缓存的批量维护。

rank 采用小榜变化后立即同步批量刷新的简单策略，旧录像 id 直接从 rank hash 获取，member 使用十进制 `user_id:video_id`。score 使用 `M = 2**26` 和 Unix epoch 起点，保留整数毫秒用时和分钟级上传时间，准确还原 `timems`；日常增量更新直接比较 score，重建可按原始上传时间选优。性能优先，不预先增加并发保护，实际出现问题后再处理。面向受影响人数达到 1000 人及以上的优化留到服务器升级时再评估，先保持单项可修复、整榜可重建。
